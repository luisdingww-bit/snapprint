# SnapPrint 社区版部署

SnapPrint 社区版只依赖 `trimesh` + `FastAPI`，**无需显卡、无需任何模型权重**。
后端同时托管 `web/` 静态前端，因此「前端 + 后端」是同一次进程，部署极简。

## 一、本地运行

```bash
pip install -r requirements.txt
python -m app.main
# 或： python scripts/start_backend.py
```
打开 http://localhost:8000 。

要可复现安装，可用锁文件：
```bash
pip install -r requirements.lock.txt
```

## 二、云部署（CloudStudio / 任意主机）

社区版是单进程 Web 服务，把仓库部署到任意能跑 Python 的机器即可：

```bash
git clone <your-repo> snapprint && cd snapprint
python -m venv .venv && source .venv/bin/activate
pip install -r requirements.txt
python -m app.main          # 默认端口 8000，可用 PORT 环境变量覆盖
```

监听端口由 `PORT` 环境变量控制（默认 `8000`）。
建议用进程管理器（systemd / supervisor / pm2）保活，并用 Nginx 反代。
数据库 `data/snapprint.db` 与上传文件 `outputs/uploads/` 默认在仓库目录内，
多实例部署时请挂载同一数据目录或改用外部存储。

## 三、静态前端 + 独立后端（Surge / CloudStudio / Pages 等）

> ⚠️ 纯静态托管（Surge / CloudStudio / GitHub Pages）**跑不了 Python 后端**，
> 因此画廊 / 上传 / 评论等需要后端的接口在该模式下会显示「后端未连接」。
> 要让社区完整可用，后端必须跑在一台有公网地址的机器上。

若把前端放到静态托管、分析后端自托管：

1. 后端按第二节部署到一台有公网地址的机器（如 `https://api.your-host.com`）；
2. 前端 `web/` 是纯静态文件，直接 `surge web`（Surge）或推到 Pages / CloudStudio；
3. 在前端 `web/config.js` 把 `API_BASE` 改成你的后端地址：
   ```js
   window.SNAPRINT_CONFIG = { API_BASE: "https://api.your-host.com" };
   ```
4. 后端设置环境变量收紧跨域（见第五节）：
   ```
   SNAPRINT_CORS_ORIGINS=https://your-static-site.com
   ```

## 四、Docker（推荐自托管）

仓库内含 `Dockerfile` + `docker-compose.yml`，一条命令起完整社区（前端+后端一体）：

```bash
docker compose up --build -d
```

- 容器内以 `python -m app.main` 启动，端口 8000（宿主机同样映射 8000）；
- **数据已持久化**：`docker-compose.yml` 把 `data/` 与 `outputs/uploads/` 挂成卷，
  容器重建 / 升级不丢社区数据库与模型文件；
- 想换端口：`ports: "8080:8000"` 改左边即可；想加鉴权见第五节。

## 五、环境变量（加固）

| 变量 | 默认 | 说明 |
|---|---|---|
| `PORT` | `8000` | 监听端口（仅 `__main__` 直接运行时生效） |
| `SNAPRINT_API_KEY` | 空 | 设置后所有 `/api/*` 需携带请求头 `X-API-Key` |
| `SNAPRINT_RATE_LIMIT` | `0` | 每客户端每分钟请求上限（0=不限） |
| `SNAPRINT_CORS_ORIGINS` | 公开 Demo+本地 | 逗号分隔的可信前端来源 |
| `SNAPRINT_MAX_UPLOAD_MB` | `50` | 单文件大小上限（MB） |

示例（内网小团队）：
```bash
export SNAPRINT_API_KEY="你的密钥"
export SNAPRINT_RATE_LIMIT=30
export SNAPRINT_CORS_ORIGINS="https://snapprint-3d.surge.sh,http://localhost:8000"
python -m app.main
```

## 六、数据说明

- **社区数据库**：`data/snapprint.db`（SQLite）。首次运行自动建表，已加入 `.gitignore`。
- **模型原文件**：`outputs/uploads/<id>.<ext>`。详情页可下载，已加入 `.gitignore`。
- 备份只需复制这两个目录；迁移换机器直接带走即可。

## 七、Railway 免费托管（推荐：零服务器运维）

Railway 能从 GitHub 仓库一键拉起 FastAPI 服务，免费额度足够社区起步。
项目已内置 `railway.json`（Nixpacks 构建 + `uvicorn app.main:app` 启动 +
`/api/health` 健康检查）与 `runtime.txt`（锁定 Python 3.11）。

### 部署步骤
1. 打开 <https://railway.app> 用 **GitHub 账号登录**；
2. 点 **New Project → Deploy from GitHub repo**，授权并选择 `luisdingww-bit/snapprint`；
3. Railway 自动检测 Python 项目，按 `railway.json` 构建并启动；
4. 在 **Settings → Variables** 按需添加环境变量（见第五节），例如：
   - `SNAPRINT_API_KEY`：给公网社区上把锁（强烈建议）；
   - `SNAPRINT_RATE_LIMIT=30`：防刷；
   - `SNAPRINT_CORS_ORIGINS`：若前端与后端不同源，填前端域名。
5. 在 **Settings → Domains** 生成 `xxx.up.railway.app` 域名；
6. 打开该域名即访问完整社区——前端 `web/` 由后端同源托管，无需额外配置。

### 让已有静态前端（Surge / CloudStudio）连 Railway 后端
若保留 Surge / CloudStudio 的静态前端，把其 `web/config.js` 的
`API_BASE` 改为 Railway 域名并重新部署该静态站点；同时后端设置
`SNAPRINT_CORS_ORIGINS` 包含该前端域名即可跨域访问。

### 数据持久化（重要）
Railway 免费层文件系统是 **ephemeral（临时）** 的：每次重新部署会重置未挂卷的目录，
**社区数据库与上传文件会丢失**。
- 起步 / Demo 阶段可接受（数据随重部署重置）；
- 要长期保留：在 Railway **创建 Volume** 挂到 `/data`，并在 Variables 设
  `SNAPRINT_DATA_DIR=/data`——`app/db.py` 已支持该变量，数据即落盘到持久卷
  （Railway Volume 为付费项，详见 Railway 账单说明）；
- 或迁移到外部数据库（如 Turso/libSQL、Supabase Postgres），需替换 `app/db.py`。
